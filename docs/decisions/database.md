## Q: SQLite vs PostgreSQL?

**초기 결정**: SQLite

**이유**:
- 파일 기반으로 간단한 설정
- 소규모 애플리케이션에 적합
- Docker 볼륨으로 간편한 데이터 영속성
- 자택 환경에 충분
- 설정 없이 바로 사용 가능

**대안**: PostgreSQL
- 장점: 동시성, 복잡한 쿼리, 확장성
- 단점: 추가 컨테이너 필요, 설정 복잡도 증가

**향후 계획**:
- 성능 이슈나 동시성 문제 발생 시 PostgreSQL로 전환
- SQLAlchemy 사용으로 마이그레이션 용이

**PostgreSQL 전환 시나리오**:
- 동시 접속자 10명 이상
- 복잡한 쿼리 및 인덱싱 필요
- 데이터 무결성 강화 필요
- 백업/복구 정책 필요

**날짜**: 2025-11-21

## Q: Event 모델의 날짜/시간 필드는 왜 String인가요?

**결정**: `event_date`는 String (YYYY-MM-DD), `event_time`은 String (HH:MM)

**이유**:
- 프론트엔드와의 간단한 데이터 교환
- 날짜 기반 필터링 쿼리 단순화 (`WHERE event_date = '2025-11-21'`)
- 타임존 문제 회피 (로컬 이벤트 중심)
- HTML input[type="date"]와 직접 호환

**대안 고려**: DateTime 타입
- 장점: 날짜 연산 가능, DB 수준 정렬
- 단점: 타임존 처리 복잡도 증가, 현재 요구사항에서는 불필요

**결과/영향**:
- API 응답 간소화
- 프론트엔드 변환 로직 불필요
- 날짜 필터링 성능 우수

**제한사항**:
- 날짜 범위 쿼리 시 문자열 비교 (현재는 문제없음)
- 추후 날짜 연산 필요 시 PostgreSQL의 DATE 타입으로 전환 가능

**날짜**: 2025-11-21

## Q: 좌표 데이터는 어떻게 저장하나요?

**결정**: latitude, longitude를 Float 타입으로 저장

**이유**:
- Geocoding API로 주소 변환 시 한 번만 저장
- 런타임에 API 호출 불필요 (비용 절감)
- 지도 마커 표시에 바로 사용 가능

**데이터 흐름**:
```
사용자 주소 입력
   ↓
Geocoding API (프론트엔드)
   ↓
좌표 획득 (lat, lng)
   ↓
DB에 저장
   ↓
이후 조회 시 API 호출 없이 사용
```

**결과/영향**:
- Google Maps API 비용 대폭 절감
- 응답 속도 향상
- 오프라인 환경에서도 지도 표시 가능 (API 키만 있으면)

**날짜**: 2025-11-21
